# /setup-engine — Section 7.5: Scaffold the Engine Project

> Part of `/setup-engine`. `SKILL.md` names when to read this file; the settings it
> resolved and the rules under its later headings still apply here.

## 7.5 Scaffold the Engine Project

**Without this step the framework produces source files no engine can open.**
`/dev-story` writes `.gd`/`.cs`/`.cpp`/`.rs` under the resolved code root, and the `minimal` path
advertises "four steps to running code" — but no other skill writes a
`project.godot`, a Unity project, a `.uproject` or a `Cargo.toml` for the engine to load.

### Godot — write `project.godot` if one is absent

**Never overwrite an existing `project.godot`.** If the file is already there,
say so and skip to Section 8 — the developer has a project and its settings are
theirs.

Show the proposed file, then ask: *"May I create `project.godot` at the repo
root?"* On approval, write:

```ini
config_version=5

[application]

config/name="<project name>"
config/features=PackedStringArray("<major.minor>", "<renderer feature>")

[rendering]

renderer/rendering_method="<rendering method>"
```

Fill it from decisions already made — do not ask again:

| Field | Source |
|-------|--------|
| `config/name` | the brief's working title, else the repo directory name |
| `<major.minor>` | `engine.version` from Section 3, major and minor only (`4.7.2` → `4.7`) |
| `<renderer feature>` / `<rendering method>` | the `rendering` value chosen in Section 5.5.1 — Compatibility → `"GL Compatibility"` / `gl_compatibility`; Forward+ → `"Forward Plus"` / `forward_plus`; Mobile → `"Mobile"` / `mobile` |

**Leave `run/main_scene` unset.** There is no scene yet at engine-setup time.
Add a comment saying `/dev-story` or the developer sets it once a scene exists;
an empty project with no main scene opens fine in the editor.

**Then verify, and report what the verification actually was.** If the engine
binary was found in Section 3, run its headless import
(`godot --headless --path . --import`) and report the result — read the output
for `ERROR`, because the import exits 0 even when something in the project
fails to load. On Godot 4.7, this first import of a new project sometimes exits
139 (a crash on exit) after it has finished; run it once more and report the
second result. If the binary was
not found, or its version differs from the pinned one, write
**`project.godot NOT VERIFIED — <reason>`**. The `config_version` and feature
strings are stable across Godot 4.x, but "stable in the versions I know" is not
the same as "checked against the version you pinned", and only the run
establishes the latter.

### Bevy — write the Cargo project if `Cargo.toml` is absent

**Never overwrite an existing `Cargo.toml`.** If one is already at the root the
developer has a crate and its layout is theirs: say so and skip to Section 8. A
Bevy project is a plain Cargo crate, every file of which is text this skill can
source, so unlike Unity and Unreal it is written here rather than delegated to an
editor.

Show the proposed files, then ask: *"May I create `Cargo.toml`, `src/lib.rs`,
`src/main.rs`, `tests/unit/main.rs` and `assets/` at the repo root?"* On
approval, write them, with `<crate>` the brief's working title in snake_case
(else the repo directory name), and `<major.minor>` the `engine.version` from
Section 3.

`Cargo.toml`:

```toml
[package]
name = "<crate>"
version = "0.1.0"
edition = "2024"

[dependencies]
bevy = "<major.minor>"

# Enable a small amount of optimization in the dev profile.
[profile.dev]
opt-level = 1

# Enable a large amount of optimization in the dev profile for dependencies.
[profile.dev.package."*"]
opt-level = 3
```

The two profile blocks, comments included, are bevy.org's own "Compile with
Performance Optimizations" settings
(<https://bevy.org/learn/quick-start/getting-started/setup/>, checked
2026-11-02): without them a debug build of a Bevy game can run too slowly to
play, and the page advises against developing in release mode instead. Nothing
else from that page is written. Its other settings — dynamic linking, an
alternative linker, the nightly Cranelift backend, release and Wasm profiles —
are marked optional there and depend on the developer's OS and toolchain, so
they are the developer's call, not a default. `edition = "2024"` is the edition
the same page shows (on 2026-11-02 its example still pinned `bevy = "0.19"`; the
version here comes from Section 3, not from that page).

`src/lib.rs` — the game's logic lives in the library crate, because Cargo's
integration tests under `tests/` can reach only its `pub` items:

```rust
//! The game. Its logic lives in this library crate: `main.rs` only builds the
//! `App`, and the tests under `tests/` can reach only what this crate makes `pub`.

use bevy::prelude::*;

/// The game's root plugin. Add each system's own plugin to it as it is written.
pub struct GamePlugin;

impl Plugin for GamePlugin {
    fn build(&self, _app: &mut App) {}
}
```

`src/main.rs`:

```rust
use bevy::prelude::*;
use <crate>::GamePlugin;

fn main() {
    App::new().add_plugins((DefaultPlugins, GamePlugin)).run();
}
```

`tests/unit/main.rs` — one test binary for every unit-test file, plus one test
that proves the headless pattern runs:

```rust
//! Unit tests against the game's pub API, built by Cargo as one test binary.
//! A file in tests/unit/ is compiled only when it is declared here as
//! `mod <system>;` -- an undeclared one is silently skipped.

use bevy::prelude::*;
use <crate>::GamePlugin;

#[test]
fn game_plugin_builds_headless() {
    let mut app = App::new();
    app.add_plugins((MinimalPlugins, GamePlugin));
    app.update();
}
```

`assets/` — Bevy's default asset folder, with an empty `assets/.gitkeep` so git
keeps it before the first asset exists. The template's `.gitignore` already
ignores Cargo's `target/` build output; check that the project's still does.

**Then verify, and report what the verification actually was.** If
`cargo --version` answered in Section 3, run `cargo check --all-targets` (the
`commands.smoke` value) and report its exit code and any `error[E…]` lines. It
writes `Cargo.lock`, which Section 8.5's read-back compares with
`engine.version`. Say before starting that a first run downloads and compiles Bevy
and its dependencies — a 0.20.1 lockfile holds 573 packages — which takes
minutes, and give it a long timeout. Exit 0 means the crate compiled; 101 means
it did not. On exit 0, if Section 7 recorded `Installed at pin time` as NOT
DETERMINED (there was no `Cargo.lock` when Section 3 probed), read the version
the new `Cargo.lock` locks for the package named exactly `bevy` and ask "May I
record `Installed at pin time: <version> (Cargo.lock)` in
`docs/engine-reference/bevy/VERSION.md`?" — otherwise Section 8.5 reports a
probe that never ran for a version that is now on disk. These exact files compiled and their test passed under
`cargo check --all-targets` and `cargo test` on Bevy 0.20.1 with rustc 1.99.1.
If cargo did not answer or the user declines the build, write
**`Cargo project NOT VERIFIED — <reason>`**: compiling on 0.20.1 is not
compiling against the version this project pinned, and only the run establishes
the latter.

### Unity and Unreal — instruct, do not fabricate

A Unity project and an `.uproject` are editor-generated and span many files,
several of them binary or machine-specific. This repo cannot source their
correct contents, and a hand-written scaffold would be the exact failure
Section 7's sourcing rule forbids — something that looks finished and is quietly
wrong.

Tell the user, in one short block, that CCGS does not create the project for
these engines and they should create it first:

- **Unity** — create the project in Unity Hub at the repo root, choosing the
  template matching the 2D/3D answer from Section 2, then re-run `/setup-engine`.
- **Unreal** — create the project in the Epic launcher or via `UnrealEditor`,
  then re-run.

Report the outcome in the Section 12 summary either way — created, already
present, or "not created, engine requires the editor" — so the user leaves this
skill knowing whether a runnable project exists.

> **Deliberately not a `project.yaml` key.** An `engine.project_scaffolded` flag
> would be written here and read by nothing, which is a dead setting — the same
> writer-without-reader defect the config gates exist to catch. The filesystem is
> the source of truth: any skill that needs to know globs for `project.godot`,
> `*.uproject`, `ProjectSettings/ProjectVersion.txt`, or a `Cargo.toml` with a
> `bevy` dependency.
